MOD API 1 · EARLY PREVIEW

Your code.
Your game.

Write mods in files. Load them from the Mods menu. No DLL injection, no client restart, no in-game editor.

This is RustTD6's own mod format. BTD6 MelonLoader mods do not run in it.

Make your first mod

  1. Install RustTD6 and Python 3.10 or newer. The SDK is included at tools/modsdk.py.
  2. Save this as mods/quickstart/mod.py, next to your game:
# The SDK supplies Mod when it builds this script.
mod = Mod("quickstart", "Quick Start", description="A custom dart, bloon and mode.")

dart = mod.tower("dart", base="DartMonkey", cost=100)
dart.projectile(damage=3, pierce=4)
dart.weapon(rate=0.5)

mod.bloon("durable-red", base="Red", maxHealth=5)
mod.mode("training", base="Medium", cash=2000, lives=300)

Download the example

  1. From the installation folder, build its manifest:
python tools/modsdk.py build mods/quickstart/mod.py
  1. Enable Settings → Advanced → UI → Show Mods Button. Open Mods, press Reload Mods, flip the switch beside Quick Start. Select its row to inspect its properties and settings.
  2. Start a new local game. Your new tower appears in the shop. Your new bloon appears in Sandbox. The mode screen has a custom-mode selector.

Your script runs only when you explicitly build it. The game reads its generated mod.json and compiles the definitions into its native simulation. You can generate the same JSON using another language.

Reload, don't restart

Edit your code, build again, then reload the mod list. Changes apply to the next new game or restart of a game. An existing match keeps its current definitions; changing live entities underneath it is not supported yet.

Enable/disable is separate from selection. Optional per-mod settings save locally. The manager is for installed mods and settings, not authoring.

The content API

A manifest has api_version, a unique lowercase id, name, version, and a content list. Keep your ID stable between releases. The SDK prefixes your content IDs with your mod ID.

Towers and projectiles

mod.tower(name, base="DartMonkey", **patch) clones the tower, its upgrade tiers and shared visual references, then adds it to the shop. Custom towers can reuse exported art or load author-owned baked models. Shop icons currently reuse the cloned tower’s art. See Custom models below. Heroes cannot be used as clone bases.

tower.projectile(damage=3, pierce=4) edits the base tier's projectile. tower.weapon(rate=0.5) sets its shot interval in seconds. Pass tier="100", attack=0 or weapon=0 to edit another tier or weapon. Upgraded tiers keep their inherited values unless edited separately.

Reuse another native projectile with a build-time template:

bomb = mod.projectile("big-bomb", base_tower="BombShooter", damage=10)
dart.projectile(bomb, pierce=30)

Projectiles are compiled native data attached to weapons. They are not Python objects or callbacks during play.

Bloons and rounds

mod.bloon("durable-red", base="Red", maxHealth=5) creates a new bloon using an existing visual. speed, radius, children, isCamo and supported native behaviors can be edited. Child references must exist and cannot form cycles.

Use mod.set to replace a round group with one referencing your new bloon, or send it from Sandbox. New arbitrary behaviors require an engine API addition.

Modes and global changes

mod.mode("training", base="Medium", cash=2000) adds a new mode. It is available in the custom-mode selector below the ordinary modes.

mod.all_modes(lives=500) patches every mode present at that point in the content list. To change only an existing mode:

mod.set("/modes/Medium/cash", 1500)
mod.set("/towers/DartMonkey/cost", 100)

These changes work in ordinary local games, not just Sandbox. Official events keep their own rules. In private co-op the room's mod set replaces each player's local selection.

Menus and statistics

mod.menu(page, path, text="...", visible=False) changes an existing menu node when that scene loads. Page names match exported prefab filenames, such as MainMenuUI. Paths match the node hierarchy in your local ui/prefabs export. Use text or visibility separately.

Native tower/bloon/weapon statistics are editable through content paths. Optional embedded Rhai callbacks can now create interactive in-match UI trees and native popups, keep per-match state, spawn waves and change cash/lives. New profile counters are not implemented yet. Menu values that the game updates dynamically may overwrite a load-time edit.

Raw data and validation

mod.set(path, value) replaces an existing field using a JSON Pointer. Roots are towers, tower_tiers, bloons, modes, start, rounds, round_sets and freeplay. Inspect your own local_extracted/game/game.json for native field names and supported behaviors. Do not bundle extracted game data with a mod.

Manifests are limited to 64 KiB and 256 operations. Unknown operations, duplicate IDs, missing fields, child cycles and conflicting writes to the same path are rejected. Mods compile in sorted ID order; operations within a mod run in written order.

Individual upgrades

tower.upgrade(0, 1, cost=150,
    stats={"range":40}, weapon={"rate":0.5},
    projectile={"damage":5, "pierce":5},
    model="robot-upgraded")

Paths are 0–2; tiers are 1–5. Edits carry into later tiers and crosspaths. Values are absolute replacements, so define lower tiers before higher tiers. A model swap uses its exported muzzle and release timing.

Current limits: fourth upgrade paths, arbitrary frontend screens, arbitrary new native behavior types, and custom-map registration are not implemented yet. Interactive in-match overlays and event scripts are supported. Menu text/visibility edits are supported. New low-level behavior types still require engine hooks; the current API does not expose the whole engine.

Custom models

Start with an animated robot and custom projectile. Everything in this example is original artwork:

python tools/mod_model.py template mods/throwbot
python tools/modsdk.py build mods/throwbot/mod.py

Enable Throwbot, then start a new game. Edit its code and models, press Reload Mods, and start another match. The client does not need to restart.

tower = mod.tower("robot", base="DartMonkey")
tower.model("robot")
tower.projectile(display=mod.model("bolt"), damage=3, pierce=4)

Put baked models in mods/my-mod/assets/robot/. The mod folder matches its ID. The exporter records the hand/barrel muzzle and the animation’s release time; tower.model wires these into the primary weapon across inherited upgrades.

Import an OBJ mesh
python tools/mod_model.py import robot.obj --texture atlas.png --out mods/my-mod/assets/robot --muzzle 4 8 6 --release 0.15

Y up, +Z forward, feet at the origin. Use game units (the starter is about 14 units tall). Add --attack frame01.obj frame02.obj ... to bake a throw, using identical topology and face order. Without those frames, aiming and firing work with a static model.

Export a rigged Blender animation
blender --background robot.blend --python tools/blender_mod_model.py -- --out mods/my-mod/assets/robot --idle 1 60 --attack 61 90 --release 70 --texture atlas.png

Blender Z is up, -Y forward. Add an Empty named Muzzle at the hand/barrel, parent it to the rig, and place exported meshes in a RustTD6 collection. The timeline supplies Idle, Attack and the release frame. Use a single PNG atlas and stable topology; arbitrary material shaders are not imported.

Meshes and animation poses run through the native renderer. Blender and Python never run during gameplay. Keep models light: at most 60,000 split vertices, 600 frames per clip and 128 MiB of uncompressed poses. Custom models are local-only for now; co-op reports that art transfer is unavailable rather than starting with missing files.

Mechanics, UI and shop layout

Use mod.existing_tower("DartMonkey").shop(after="SniperMonkey", category="military") to rearrange existing towers, or call .shop(...) on your new tower. Use before, after or index, and visible=False to hide an entry.

mod.script("mechanics", file="mechanics.rhai", tick_interval=60) embeds actual event code. Define round, tower, pop or tick callbacks; use this for match state and return validated commands. Build custom native UI trees, bind their buttons to your functions, open popups, queue bloons and change resources.

Development API: use the current client build; older releases may not include these hooks.

The complete example is in tools/mod_examples/workshop/, with the full command and UI contract in mods/README.md. Scripts compile once per match, have execution limits, and run only when subscribed. Python authoring scripts are never run in the client. Runtime scripts currently work in local matches.

Try the workshop

Download mod.py and mechanics.rhai into mods/workshop/. Use the updated SDK if your copy predates event scripts.

python -I tools/modsdk.py build mods/workshop/mod.py

In the client: Mods → Reload Mods → enable Mechanics Workshop → start a new local match. The example moves Dart Monkey after Sniper and adds a workshop button with a custom panel, wave spawner, popup and adjustable round reward.

Your first event script
fn on_new_game(ctx) { this.reward = 100; [] }
fn on_round_end(ctx) {
    if ctx.sandbox { return []; }
    this.reward += 10;
    [#{op: "cash", amount: this.reward}]
}

Callbacks receive a game snapshot. this keeps per-match state. Return commands to change the game; no Python runs while playing. Helpers that use state are called as this.helper(ctx).

Hooks and game commands

Hooks: on_new_game, on_round_start, on_round_end, on_tower_placed, on_tower_sold, on_towers_changed, on_pop and on_tick. Pop events aggregate one simulation step; tick intervals use 60 simulation steps per second.

Snapshot fields: cash, lives, round (completed rounds), tick, popped, tower_count, bloon_count and sandbox.

#{op: "cash", amount: 100}
#{op: "lives", value: 200}
#{op: "spawn", name: "Blue", count: 30, spacing: 0.2}
#{op: "clear_bloons"}
#{op: "reset_cooldowns"}
#{op: "popup", title: "Hello", body: "Your message"}

Return an array, such as [#{op: "cash", amount: 100}]. Commands validate together before applying. Failed scripts disable themselves for that match.

Build your own UI

Return #{op:"ui", widget:#{id:"panel", tree:node, actions:#{"Button":"on_click"}, modal:true}}. Trees use the native name / active / rect / comps / children format: text, images, buttons, masks and layout groups. Paths are relative to the widget root; an empty path binds the root itself.

Each action calls your own one-argument function. Replace the same widget ID to update it, or return #{op:"remove_ui", id:"panel"}. The workshop source includes a complete panel. This currently creates in-match overlays; arbitrary frontend screens are still pending.

Limits and performance

Callbacks have a 30,000-operation budget, 16 call levels, 32 commands and 64 KiB of persistent state. Script source is limited to 32 KiB inside the 64 KiB manifest. UI supports 64 active widgets, 128 nodes per widget, 12 levels and 32 action bindings.

Scripts compile once per match. Native attacks and projectiles remain native, and UI rebuilds only when changed. Prefer round/entity hooks to frequent ticks. Runtime scripts expose no filesystem, network or process APIs and are not yet supported in co-op.

Entities and behavior hooks

Scripts can now inspect individual towers, bloons and projectiles, edit supported fields by ID, and change or cancel native damage, emissions and purchases. These are development APIs for local matches.

Query entities and edit by ID
fn on_new_game(ctx) {
    [#{op:"inspect", query:#{kind:"bloons", offset:0, limit:8, tag:"health"}}]
}
fn on_query(ctx) {
    let edits=[];
    for b in ctx.event.items {
        edits.push(#{op:"entity_patch", patch:#{kind:"bloons",
            id:b.id, layer:b.layer, fields:#{hp:50}}});
    }
    edits
}

Query kinds: towers, bloons, projectiles. Responses include tag, offset, total and items. Pages contain up to 128 items; eight requests are serviced per simulation step. Use IDs, not array positions, as references.

Edit bloon current HP, projectile damage/pierce/velocity/remaining lifetime, or supported tower targeting modes/points. Missing entities and stale layer IDs are ignored. To deal native damage rather than assign HP, return #{op:"damage_bloon", id:b.id, layer:b.layer, amount:5}; it runs at the next simulation boundary.

Enable hooks only while needed
fn on_toggle(ctx) {
    this.enabled = !this.enabled;
    [#{op:"listen", event:"before_fire", enabled:this.enabled}]
}
// Apply the last shield charge, then stop receiving damage callbacks:
fn before_damage(ctx) { #{cancel:true, unsubscribe:true} }

Callbacks start subscribed. A listen command pauses or resumes a declared callback in the same script without clearing state or widgets. UI buttons can turn it back on. Interceptors can unsubscribe only their current hook after its final decision. Other mods stay subscribed.

When no owner listens, the native hook skips script execution and entity snapshots. Entity Lab turns attack hooks on only while their features are enabled, and stops its periodic refresh when closed. An unknown callback name rejects the whole command batch.

Change or cancel behavior
fn before_damage(ctx) { #{damage:ctx.event.damage*2} }
fn before_fire(ctx) { #{damage:ctx.event.damage*2, count:3} }
fn before_place(ctx) {
    #{cancel:ctx.event.tower=="BananaFarm"}
}
fn before_sell(ctx) { #{cancel:ctx.event.tower=="DartMonkey"} }
fn before_upgrade(ctx) { #{cancel:ctx.event.paragon} }

Interceptors return a map, rather than an array of commands. An empty map preserves the action. Damage hooks can change the amount or cancel health loss; emission hooks can change damage, count, speed, pierce or direction, or cancel the emission. Place, sell and upgrade hooks can veto the action.

Damage is intercepted once before recursive child-layer overflow. Cancelling damage does not cancel other hit effects; cancelling an emission does not refund its cooldown. Whole-bloon destruction that bypasses health damage has no damage callback. Emission hooks also see sub-projectiles. Forced dependent-sale cleanup bypasses child sell vetoes.

Scripts compose in stable order; later hooks see earlier overrides. Cancellation stops the action. No game commands run from inside an interceptor. A shared 100,000-operation budget per simulation tick supplements the per-callback limit. Failed subscriptions leave the hot path; no subscriber means no script call or entity snapshot.

Try Entity Lab

Download mod.py and entities.rhai into mods/entity-lab/.

python -I tools/modsdk.py build mods/entity-lab/mod.py

Reload Mods, enable Entity Lab and start a new local match. Its panel can inspect towers, add 50 HP to a specific bloon, double projectile damage, absorb five health hits and block Farm purchases. The toggles demonstrate real behavior hooks; they do not rewrite base game data.

Full payloads, units, field limits and timing rules are in the complete API reference. Fourth upgrade paths, unrestricted engine writes and synchronized script mods remain future work.

Mods with friends

Host a private iroh room, then open Room Mods. The host chooses the set. Guests can inspect it, and receive its data directly from the host even if it is not installed locally. Received manifests stay isolated in the room; they do not replace installed mods or run author scripts.

The current transfer supports up to 16 data mods, totaling 24 KiB of manifest text. Runtime script mods, custom art packs and large file transfers are not supported in co-op yet. Each package is hash-checked, changes clear everyone's Ready state, and all players must have the same client build and base game data. The normal load barrier also checks the compiled initial game state before play.

Room mods are locked once a match starts. Official-server interoperability is not implemented. Use a private RustTD6 room.

Client and asset updates

Installed builds check GitHub through the launcher. A code-only compatible update installs automatically. If a release needs new extracted assets, you can keep playing the installed version or run the setup DLL inside BTD6 again. The launcher stages new assets and keeps the old build intact if extraction fails. Offline play uses the installed build.
